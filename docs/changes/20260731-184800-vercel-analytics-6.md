# Vercel Web Analytics + Speed Insights

The site now also ships Vercel's own first-party monitoring, on top of the
existing Google Analytics setup (`documentation/google-analytics.md`):

- **`@vercel/analytics`** — pageview/traffic analytics (Vercel's "Web
  Analytics" product).
- **`@vercel/speed-insights`** — real-user Core Web Vitals (Vercel's "Speed
  Insights" product).

This is purely additive. `AnalyticsService`
(`src/app/services/analytics/analytics.service.ts`) and the `gtag.js`
integration it wraps are untouched — there are now two independent
analytics integrations running side by side, same as how this codebase
already keeps the GA tag as a standalone concern rather than folding
everything into one service.

## Where it's wired in

Both libraries ship a framework-agnostic `inject()`-style entry point
(root package export, distinct from their React/Next-specific
`@vercel/analytics/react` etc. subpaths), which just injects a `<script>`
tag and sets up a `window.va`/`window.si` event queue — no component tree
or JSX required, so it drops into this non-Next Angular app cleanly.

- [`src/app/app.component.ts`](../src/app/app.component.ts) —
  `ngOnInit()` calls `inject()` (aliased `injectVercelAnalytics`) from
  `@vercel/analytics` and `injectSpeedInsights()` from
  `@vercel/speed-insights`, right after the existing `Title`/`Meta` setup.
  This runs once, app-wide, at bootstrap — the same "initialize once in
  root `ngOnInit`" pattern already used here (mirrors how `ThemeService`
  resolves its initial mode synchronously on construction, and how
  `AppComponent.ngOnInit()` already does one-time, app-wide setup for the
  page `<title>`/meta tags).
- Guarded with Angular's `isPlatformBrowser(this.platformId)` (via
  `PLATFORM_ID` injection) before calling either `inject()`. This project
  currently has **no SSR** (`main.ts` bootstraps with `platformBrowser()`
  only), so the guard is not strictly load-bearing today, but it's cheap
  insurance against the in-flight SSR/prerendering work landing in a
  sibling branch — without it, an `ngOnInit` that runs during server-side
  rendering would otherwise rely solely on the libraries' own internal
  `typeof window` checks (see below) rather than failing fast/obviously at
  the call site.

No new files, no changes to `analytics.service.ts`, `index.html`, or the
`GOOGLE_ANALYTICS_ID` build-time injection pipeline.

## No environment variables needed — verified, not assumed

Read both packages' generic entry points directly
(`node_modules/@vercel/analytics/dist/index.mjs` and
`node_modules/@vercel/speed-insights/dist/index.mjs`, `v2.0.1` /
`v2.0.0`) rather than taking this on faith:

- Both `inject()` functions start with `if (!isBrowser()) return;`
  (`isBrowser` = `typeof window !== 'undefined'`) — inert under Node/SSR
  with no guard of our own needed, confirming the Angular-side
  `isPlatformBrowser` check above is belt-and-braces, not required.
- Neither takes a DSN, project ID, or measurement ID by default. They
  append a `<script src="/_vercel/insights/script.js">` /
  `<script src="/_vercel/speed-insights/script.js">` tag — a
  **relative, same-origin** path. On an actual Vercel deployment, Vercel's
  edge layer intercepts that specific path and serves the real collector
  script (only if Web Analytics / Speed Insights is turned on for the
  project in the dashboard); off Vercel, or with the feature disabled,
  that path simply 404s.
- Each script tag has an `onerror` handler that does `console.log(...)`
  (not `console.error`, and nothing is `throw`n) — e.g. `[Vercel Web
  Analytics] Failed to load script from /_vercel/insights/script.js. Be
  sure to enable Web Analytics for your project and deploy again.` So a
  404 shows up as a quiet log line, never an uncaught exception or a
  broken page.
- `mode: 'auto'` (the default) is resolved from `process.env.NODE_ENV`
  inside a `try { … } catch { }`, defaulting to `'production'` on any
  failure to read it (e.g. no `process` in the browser bundle) — this
  can't throw either.

**Conclusion:** the "no env-var plumbing, no-op off Vercel" premise holds.
Nothing needs to be added to `vercel.json`, `scripts/inject-env.js`, or the
Vercel dashboard for this to work — enabling Web Analytics / Speed
Insights for the project (Vercel dashboard → Project → Analytics /
Speed Insights tabs) is the only remaining step to start seeing data, and
that's a dashboard toggle, not a code or env-var change.

## Verified locally

- `npx ng build` — succeeds, no new errors (one pre-existing, unrelated
  budget warning on `header.component.scss`).
- Served the production build (`http-server dist/v3.yannislam.org/browser`)
  and loaded it in headless Chromium (Playwright): no uncaught page
  errors. The two Vercel script requests 404 as expected (this isn't a
  Vercel deployment) and log the quiet `console.log` warning described
  above; `window.va` and `window.si` (the client-side event queues both
  libraries install before their script loads) are present as functions,
  confirming `inject()`/`injectSpeedInsights()` ran.
